Design decisions, and two exceptions

Normalised

  • Platforms: 4 boolean columns → an N:M table, so a new platform is a row.
  • Tags: JSON list → tags + game_tags (1NF), keeping Steam's order in tag_rank.
  • Rating labels → lookup table with rank_order (worst → best).
  • users.reviews dropped: derived, and it would go stale after any INSERT or DELETE.

Kept on purpose

  • Exception 1 · rating is almost derivable from ratio + review count, but Steam's rule is not published and ranges overlap. Recomputing it would invent a rule.
  • Exception 2 · user_reviews, positive_ratio look like aggregates of recommendations, but they are store-wide totals. Q05 shows they differ from the sample.
  • Early-access reviews stay: real reviews, studied in Q06.

The dashboard: SQL in, charts out

  • 11 tabs, 13 charts, each fed only by the rows of one query.
  • Every filter goes to SQL as a bound parameter %(tag)s; the user never types SQL.
  • '; DROP TABLE games; -- is searched as plain text.
  • Bad input shows a message: limited widgets, 120 s timeout, rollback on any error.
  • The sale simulation runs an UPDATE, then ROLLBACK.

How AI was used, and what I learned

AI adoption

  • Claude Code drafted the profiling queries, schema, ETL, queries, app and report.
  • Every output was checked: row counts against the files, query samples by hand, plans with EXPLAIN, the app with AppTest and bad inputs.
  • Full table in section 7 of the report.

Lessons

  • Profile first: the duplicates and the price placeholder only appear when you count.
  • One transaction makes a 9-minute load safe to fail.
  • An FK constraint does not create an index.
  • Big sorts need memory limits: a 1 GB work_mem per worker filled the laptop's RAM once.
